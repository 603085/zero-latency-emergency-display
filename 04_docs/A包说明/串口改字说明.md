# 串口改字（Task A 扩展项）使用说明

**功能**：用 PC 的串口终端，把屏幕上的滚动字幕换成任意一行 ASCII 文字。

---

## 零、上板前必须先做这一步（否则 TD 会报错）

**新增了两个 `.v` 文件，必须先在 TD 工程里登记。**

TD 的工程文件 `HDMI1.4b_Transmitter_v1.0.al` 是**逐个文件列路径**的，不是扫描目录。
所以往 `hdl_source` 里放新文件，TD **完全不知道**，直接 Run 会得到：

```
ERROR: uart_text(MSG_LEN=16,CLK_FREQ=25000000,BAUD=115200) is a black box
       in ../../../user_source/hdl_source/video_layers_top.v(541)
```

**这不是 RTL 写错了。** "black box" 的意思是：TD 看见有人例化了 `uart_text`，
但**从来没编译过这个模块的定义**，只好当成一个空盒子。
（它没提 `uart_rx`，因为 `uart_rx` 只被 `uart_text` 例化，而 `uart_text` 本身就没进来。）

三种做法，**任选一种**：

### 做法 A：从资源管理器拖进去（最不容易点错，TD 开着也行）

1. 打开资源管理器，进 `lab_ex5_i2s\src\user_source\hdl_source\`
2. 选中 **`uart_rx.v`** 和 **`uart_text.v`**（Ctrl 点两下）
3. 直接**拖到 TD 左侧的源文件列表里**松手

### 做法 B：TD 菜单

TD 里右键工程/设计节点 → **Add Files…** → 选上面那两个 `.v` → 确定。

### 做法 C：改工程文件（**必须先关掉 TD**）

双击 `rtl\add_uart_files_to_td.bat`。
它会**等你关掉 TD**，然后自动备份 + 插入 + 校验。

命令行等价写法：

```bash
python rtl\td_add_uart_files.py --wait 600
```

> **为什么做法 C 一定要关 TD**（这是实测过的，不是理论）：
> ① TD 编译用的是**内存里的**文件列表，在它开着的时候改工程文件
> 对「它会编译什么」毫无影响 —— 你会照样收到同一个 black box 错误，
> 然后以为工具坏了；
> ② TD 下次保存工程会把内存列表写回去，**悄悄把你的修改冲掉**。
> 所以脚本检测到 `td.exe` 在跑就直接拒绝执行（除非 `--force`），
> 而且拒绝时**一个字节都不写**。这个守卫是实测验证过的。

**做完之后**：Run → PROGRAM_SRAM。`uart_rx` / `uart_text` 必须出现在
TD 的源文件列表里，否则还是 black box。

## 一、硬件接线

板上**不需要接任何杜邦线** —— HX4S20C 自带了 USB 转串口芯片。

| 项 | 内容 |
|---|---|
| 接口 | 开发板**左侧的 Type-C 口**（手册第⑦项 `USB转UART`，同时兼作 5V 供电） |
| 芯片 | **CH340** |
| FPGA 引脚 | **RXD = F12**（输入，内部上拉） |
| 串口参数 | **115200 8N1**，无流控 |
| 同一根线还负责 | 供电。插上后设备管理器里会多出一个 COM 口 |

> **注意**：这个 Type-C 口和下载用的 JTAG 不是同一个口，两个都要插：
> JTAG 负责 `PROGRAM_SRAM`，Type-C 负责串口 + 供电。

**引脚依据**（三处独立来源一致）：

1. 《HX4S20 开发板手册 HDL版2410》第 11 页 §⑦「串口引脚分配表」：`RXD → F12`, `TXD → D12`
2. 开发板原理图 `3_原理图\开发板原理图\2_FPGA.pdf`：网络标号 `RXD` 与 F12 同脚位
3. 厂商例程《16_串口通信设计》约束原文：
   `set_pin_assignment { uart_rx } { LOCATION = F12; IOSTANDARD = LVCMOS33; PULLTYPE = PULLUP; }`

**`PULLTYPE = PULLUP` 是必须的**，不是可选优化：串口空闲是高电平，拔掉线后引脚若悬空，
接收机会把噪声当成起始位，不断往字幕缓冲里塞乱码。

## 二、怎么用

```bash
# 先看有哪些串口（蓝牙口会被标出来，别选错）
python send_text.py

# 发一行就退出
python send_text.py COM3 "FIRE EXIT NOW"

# 交互模式：输入一行回车发一行（推荐）
python send_text.py COM3

# 循环发送，做演示
python send_text.py COM3 "EVACUATE" --loop 5
```

需要 `pyserial`：`pip install pyserial`

也可以用任意串口助手（SSCOM / XCOM / PuTTY），设 **115200 8N1**，
敲一行字，**按回车**。

## 三、协议（故意做成最简单的形式）

| 输入 | 行为 |
|---|---|
| 可打印 ASCII `0x20~0x7E` | 追加到正在输入的这一行 |
| **CR (0x0D) 或 LF (0x0A)** | **提交**：整行替换屏幕字幕 |
| **静默约 0.8 秒** | **提交**（安全网，见下） |
| BS (0x08) 或 DEL (0x7F) | 删掉最后一个字符 |
| 缓冲区满（16 字符） | 提交，第 17 个字符丢弃 |
| **空行（直接回车）** | **什么都不做** |
| 其它字节 | 忽略 |

* **`CR LF` 只算一次提交**，因为绝大多数终端回车都会发 `\r\n`。
* **空行不提交**。回车打在空行上不会清屏 —— 否则一个多余的回车就能把告示屏擦掉。
  想清屏就发**一个空格**。
* **只支持 ASCII，而且字模里有字的只有这些：`0-9 A-Z 空格 : - . / >`**
  * **小写 `a-z` 会被自动折成大写**（字模里**根本没有小写字形**，见第九节 · 坑 3）
  * **其它标点（`!` `,` `?` …）会被直接丢掉**，不会留下看不见的空格
  * 中文会以 UTF-8 字节（≥ 0x80）发过来并被丢弃，不会显示成乱码

### 为什么加了"静默 0.8 秒自动提交"

因为**很多串口助手点「发送」时不会补换行**。
没有这条规则的话，你发一次字符串，FPGA 收到了、数码管也加一了，
但**永远等不到回车，字幕就永远不更新** —— 看起来就像"收到了但没显示"。

现在：**按回车立刻换；不按回车，0.8 秒后也会换。** 两种都行。
（0.8 秒远大于一个字符串内部字符之间的间隔 87 µs，所以整串不会被截断。）

### 为什么必须按回车（或等静默）才换字幕

如果收到一个字符就直接改屏幕，字幕会**边打字边自己重写**，
而且一旦是应急告示屏，**没打完的半句话就被播出去了**。

消息存储器 ≠ 屏幕。屏幕上是 `text_layer` 的字模缓冲，
只有 `scroll_timer` 的填充序列会重写它，而填充只在 `msg_reload` 时跑 ——
也就是只在**提交之后**。所以打了一半的行是待在消息存储器里、
**屏幕上看不到的**，屏幕永远只显示**完整的一行**。

## 四、长度：一条字幕最多 **32** 个 ASCII 字符

`MSG_LEN = 32`（原先是 16，已翻倍）。到 32 个字符时自动提交，
后面的字符开始新的一行。

### ⭐ 滚动行程会**跟着实际字数走**

这一点很重要，也是为了让加长**不破坏**你已经验收过的效果。

左右墙的位置 = **文字真正碰到屏幕边缘**的地方。如果按「最长 32 字」写死，
那么：

* 一条**短**消息只会在屏幕左半边来回晃；
* 上电那句 16 字的 `KEEP CLEAR EXIT`，会**够不到右墙** —— 也就是你验收过的效果**退回**了。

所以现在左墙右墙是按 `used_len`（这次真正提交了几个字）算的：

```
文字左边缘 x_left 应该从 0（贴左墙）扫到 H_ACTIVE - used_len*10（贴右墙）
```

**结果：不管发 1 个字还是 32 个字，永远是从左墙扫到右墙，全程不出屏。**

实测（`tb_len_bounce.v`）：

| 字数 | 左边缘扫过 | 应该 |
|---|---|---|
| 1 | 0 .. 630 | 0 .. 630 ✅ |
| 4 | 0 .. 600 | 0 .. 600 ✅ |
| 16 | 0 .. 480 | 0 .. 480 ✅ |
| 32 | 0 .. 320 | 0 .. 320 ✅ |

**而且提交之后才更新行程** —— 打一半不会让字幕在手下跳来跳去。

而且 32 字**刚好不需要动 `text_layer`**：字符下标超过 `TEXT_MAX-1`(31) 就不渲染了，
而 `char_addr` 在那里正是 5 位。再多就得同时加宽那条通路。

> 满 32 字时左右墙是 ±160，一个来回 320 px；按 0.2 秒/像素约 64 秒扫一遍。
> 想更快就调 `SCROLL_TICKS`。

## 五、上板诊断：数码管第 1 位（原空白位）

原来**空着**的那一位（`seg_data_0`）现在显示：

> **消息存储器里第 1 个字节的 低 4 位**

**这一位比"收到了几个字符"有用得多** —— 后者在坏掉的版本上也是全绿的，
因为接收机一直是好的，坏的是**写进去之后**那一段。

### 怎么读这一位

| 时刻 | 应该显示 | 说明 |
|---|---|---|
| **上电** | **`B`** | 消息是 `KEEP CLEAR EXIT `，第一个字符 `'K'` = `0x4B`，低 4 位是 `B` |
| **发一个 `7`** | **`7`** | `'7'` = `0x37`，低 4 位是 `7` |

**两个观察，各自指向完全不同的地方：**

| 现象 | 结论 |
|---|---|
| 上电**不是 `B`** | 消息存储器的**上电初值**没进去 |
| 上电是 `B`，发 `7` 之后**还是 `B`** | 收到的字节**根本没写进消息存储器** → 问题在 `msg_we/waddr/wdata` 那条路上 |
| 上电是 `B`，发 `7` 之后变成 `7` | **写进去了** → 问题在后面的填充 / 字模缓冲 / 渲染 |

**注意：写进消息存储器是"收到就写"，不需要按回车。**
所以发一个 `7`，数字就该立刻从 `B` 变 `7`。

> 为什么要专门做这个探针：前两版在 ModelSim 里**都是全绿的**，上板**都是坏的**。
> 仿真证明不了综合器会怎么建电路，所以这次的判断依据**必须来自板子本身**。

## 六、验证证据

新增两个自检 testbench，全部**驱动真实串口波形**（起始位 + 8 数据位 LSB 先 + 停止位），
用的都是**生产模块**，没有任何打桩：

### `tb_uart_rx.v` —— 10/9 项

| 检查 | 为什么必须有 |
|---|---|
| 空闲不发字节 | 否则没接线时会被噪声不停改字幕 |
| 单字节 `'A'` | 基本通路 |
| 连续两个字节 | 状态机能否回到 IDLE 并重新武装 |
| 字节 `0x00` | 起始位 + 8 个 0 = **连续 9 个低位**，接收机自我重触发的经典翻车点 |
| 字节 `0xFF` | 另一端：整帧只有一个下降沿 |
| **2 µs 毛刺被拒绝** | 掉线/噪声，比一个位（8.68 µs）短但足以伪装成起始沿 |
| **停止位为低的帧被拒绝** | 帧错误不能当成有效数据发布出去 |

### `tb_uart_msg.v` —— 23 项（端到端）

真实链路：`串口波形 → uart_rx → uart_text → scroll_timer → text_layer`

| 检查 | 为什么必须有 |
|---|---|
| **上电字幕仍是 `KEEP CLEAR EXIT`** | **兜底：加了串口不能改变「没人发数据时屏幕显示什么」** |
| 回车只触发一次提交 | |
| **消息存储器第 0 字节是 `'X'`（不是空白）** | **就是这一条抓出了上板的真 bug**，见第九节 |
| 1~15 被补齐成空格 | 短消息必须真正覆盖长消息 |
| **渲染逐像素比对** | 拿一个**独立的 `font_rom` 实例**当参照，在 `y=424` 上逐列比较 `text_alpha`。证明的是**画面真的变了**，不只是数组里有个字节 |
| **`x=248..399` 一个亮点都没有** | 旧文字真的没了 |
| 退格 | `'A','B',BS,'C'` → `AC` |
| `CR LF` 只提交一次 | |
| **空行回车不提交** | 一个多余的回车不能擦掉告示屏 |
| 16 字符不提前提交，第 17 个强制提交 | |
| **静默也能提交** | 不发换行的串口助手也能用 |
| **连续两条消息都能提交** | 「能一直更新」—— 这是用户明确要的 |
| **≥ 0x80 的字节被丢掉** | 中文/UTF-8 不能变成乱码 |

**负向对照（证明测试不是空的）**：
把补齐空格的 `(k < wr) ? line[k] : 8'h20` 临时改成 `line[k]`，
立刻报 **2 项 FAIL**。改回后全过。

## 九、⭐ 上板踩过的两个坑（这一节最值钱）

### 坑 1：在同一个 `always` 块里同时写和读同一个寄存器数组

第一版 `uart_text.v` 把正在输入的那行存在一个暂存数组里：

```verilog
reg [7:0] line [0:MSG_LEN-1];
...
line[wr] <= b;                            // 在同一个 always 块里写
msg_wdata <= (k < wr) ? line[k] : 8'h20;  // ...又在同一个块里按变量下标读
```

**这在 ModelSim 里完美跑通，18 项检查全过。**
但它**不是一个综合器有义务按你的意思实现的构造**。
TD 建出来的电路里，这个读回来是**空白**，于是每次提交都写进 16 个空格，
`text_layer` 画出 `font_rom(0)` —— **字幕整个消失**。

板上的表现完全吻合：

| 你看到的 | 原因 |
|---|---|
| 串口收到了、数码管在加一 | 接收机和计数器都是好的，**只有那次拷贝坏了** |
| 但字幕不显示 | 提交确实发生了，只是写进去的是空白 |
| 超过 16 个字之后字幕直接没了 | 第 17 个字符触发自动提交 —— **提交一发生，空白就上屏** |

**改法：暂存数组整个删掉。** 收到的字符**直接写进消息存储器**，一个字符一次写。
没有东西要拷贝，也就没有东西可以拷错。

> **为什么直接写是安全的**：消息存储器**不是屏幕**。屏幕上是 `text_layer` 的字模缓冲，
> 只有 `scroll_timer` 的填充序列会重写它，而填充只在 `msg_reload` 时跑，也就是**只在提交之后**。
> 所以打了一半的行待在消息存储器里是看不见的，屏幕永远只显示完整的一行。

**这条教训值得记住**：
> 仿真通过**不能**证明综合器会按你想的建电路。
> 凡是「同一个 always 块里用变量下标同时读写同一个数组」，都要当成可疑构造。

（对比：`scroll_timer` 里的 `msg_mem` 没有这个问题 ——
它的写和读在**两个不同的 always 块**里，就是一个标准的简单双口 RAM，综合器闭着眼都能建对。）

### 坑 2：TD 编的是 `rtl\` 里的副本，不是 `hdl_source\` 里的真源码

第一次登记文件时，路径填成了：

```
../../../../../rtl/uart_rx.v
../../../../../rtl/uart_text.v
```

`rtl\` 是**测试和镜像目录**。这样一来综合的设计是**两个目录混起来的**：
`scroll_timer.v` 来自 `hdl_source`，`uart_text.v` 来自 `rtl\`。
**平时没事，一旦两边副本不一致，板子和仿真就会莫名其妙地对不上。**

**改法**：双击 `rtl\add_uart_files_to_td.bat`。
它会**把错路径的两条删掉**，再插入 `hdl_source\` 的正确路径。

> 怎么发现的：TD 自己的综合日志 `syn_1\run.log` 里写着
> `analyze verilog file ../../../../../rtl/uart_text.v`。
> **不要只看 TD 弹出来的错误框，日志里有真话。**

### 坑 3：⭐ 字模里没有小写字母 ——「发数字可以，字母不行」

**这是上板实测报回来的现象**：发 `123` 字幕正常，**发字母什么都不显示**。

**根因不在接收、不在存储、不在渲染 —— 字模里根本没有小写字形。**

我把 `font_rom.v` 里**每一条 case 标签解码出来数了一遍**：

```
digits 0-9        have 10, MISSING  0
UPPERCASE A-Z     have 26, MISSING  0
lowercase a-z     have  0, MISSING 26
```

而且它的 `default` 分支输出 `8'h00` —— **一个像素都不画**。

所以在终端里敲 `fire exit`，每个字母都变成**完全不可见的空格**，
而 `123` 画得好好的。**在板子上看就是「数字行、字母不行」，特别像数据通路坏了。**

**改法**：在 `uart_text` 收到字符时就**折成大写**：

```verilog
wire [7:0] ch_up = ((b >= 8'h61) && (b <= 8'h7A)) ? (b - 8'h20) : b;   // a-z -> A-Z
```

顺便把**字模里没有的标点直接丢掉**（而不是存进去占一格、再画个空），
否则消息里会留下宽度不明的隐形洞。

> **教训**：现象是「某一类字符不显示」时，**第一件事是去数字模里到底有哪些字形**，
> 而不是怀疑数据通路。整个字模只有 41 个字形，一张表就能数完。
>
> 顺带一提：**大写也更适合应急告示牌。**

### 为什么动 `scroll_timer` 不会影响旧行为

`msg_we` / `msg_reload` 等新端口**悬空时不驱动**（未连接 = Z，`if (Z)` 为假），
消息存储器就保持复位值 —— 也就是原来那句 `KEEP CLEAR EXIT `。
所以**任何不接串口的旧 testbench 行为完全不变**，这一点由
`tb_uart_msg` 的第 1 项检查和原有 10 个 testbench 全绿共同保证。

### TD 综合侧（真机数据，不是推测）

我直接读了 TD 自己的综合日志 `syn_1\run.logw`，把每一条警告归到了文件上：

| 文件 | 警告数 | 归属 |
|---|---|---|
| `uart_rx.v` | **0** | 新代码 |
| `uart_text.v` | **0** | 新代码 |
| `video_layers_top.v` | **0** | 改过的代码 |
| `scroll_timer.v(96)` | 8 | **我引入的**（`char_data`），已修，见下 |
| 其余（`sdr_wrrd.enc.v` / `sd_card_cmd.v` / `afifo*.v` / `frame_read_write.v` / `top` 的 SDRAM 地址位宽） | ~60 | **改动前就有，与本次无关** |

**`scroll_timer` 那 8 条**是 `SYN-5065` ×1 + `SYN-5079` ×7：

```
SYN-5079 CRITICAL-WARNING: Register "u_video_layers/u_scroll_timer/char_data[N]"
is described with both an asynchronous reset and an asynchronous set.
```

**根因**：复位分支里写的是

```verilog
if (rst) char_data <= msg_mem[5'd0];   // ← 一个寄存器，不是常量
```

**异步复位分支里的值就是触发器的复位值，必须是常量。**
`msg_mem` 不但是寄存器，还被串口在运行时改写，TD 根本推不出它上电是什么，
于是把 `char_data` 每一位都描述成「既要异步复位又要异步置位」。改成常量
`msg_default(5'd0)` 即可。

> 只报了 bit 0~6 而不是 0~7：因为 `font_rom` 只吃 `ch1[6:0]`，
> **`char_data[7]` 真的没被用过**，TD 直接优化掉了。

**其余 `HDL-5007` 截断警告都不是我引入的**，而且都无害：
`read_addr_*` / `write_addr_*` 是 24 位接 21 位端口，丢的是高 3 位；
实际用到的地址最大 `BUF1_ADDR = 307200 < 2²¹ = 2097152`，**丢的全是 0**。
`frame_read_write.v`、`afifo*.v`、几个 `.enc.v` 同理，改动前就在。
